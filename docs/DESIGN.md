# Cupbox 播放器 · 设计与执行（v2.0）

> v2.0 变更：架构定为 **mygo（界面/渲染/音频/窗口）+ 独立解码器**。已实测 mygo 渲染能力。
> 最后更新：2026-10-18

### 2026-10-21 修正

- 浮层：鼠标在画面内移动或进入窗口时显示，静止 2 秒后淡出；停在底部 112px 操作区或拖动进度条时保持显示；离开窗口或被其它窗口遮挡时淡出。通过实时系统坐标转换到客户区坐标，避免混用旧事件坐标，兼容 DPI 缩放。5px 内轻微抖动不续期。
- 动效：按时间计算，淡入 120ms、淡出 220ms，与视频帧率无关；暂停时浮层可见期间每 100ms 检查指针，完全隐藏后停止轮询。
- 进度跳转：点击、拖动与时间提示统一按左右各 20px 的实际轨道计算，避免显示落点与实际跳转不一致。
- 启动：MP4/MOV 文件头提供完整的流参数时，不再重复调用 `avformat_find_stream_info`；缺少参数及其它容器仍保留探测。默认在 `%LOCALAPPDATA%\Cupbox\logs` 自动保留最近 20 次启动日志，只记录启动阶段、每份上限约 64KB；`CUPBOX_LOG` 仍可指定完整调试日志。每个事件带绝对时间与从 main 包初始化开始的耗时，并通过 `GetProcessTimes` 单独记录 Windows 创建进程到 main 入口的耗时（涵盖 DLL/运行时/Go 初始化）。记录视频打开、首帧解码、字幕、音频流打开、Play 调用、图标、窗口创建、首帧构建、随后 UI 回调，以及音频时钟首次推进和视频实际前进；Play 为异步启动，不等同于设备已经出声，首帧构建也不等同于 GPU 呈现完成。进程创建前的 Explorer/文件关联等待仍需外部计时。
- 首次启动慢已定位：2026-10-21 18:47 那份日志里 `process-to-main-entry=5.46s`，而同一 exe 两分钟后再启动是 17.7ms，main 之后全部阶段共 258ms。也就是说等待全在 Windows 装载 exe/DLL（加上杀软对新文件的首次检查）这一段，程序内没有任何一步慢。缓解：构建加 `-s -w`（20MB → 10.4MB，写入安装包也更小）；安装程序写完文件后运行一次 `cupbox.exe --warmup`（main 一进门就 return，不进窗口、不写日志），把首次装载/扫描的代价留在安装阶段。
- 症状与时钟：画面停在首帧不动、声音和画面都不开始，最可能是音频输出设备还在打开。旧逻辑把音频时钟当成唯一时钟，设备不推进则画面永远停在第 0 帧；现在 600ms 后画面自己走（声音会晚到，日志记 `the picture runs on its own clock`），设备就绪后记 `the sound joined ... skipped forward to the picture`。

### 2026-10-22 硬解（D3D11VA）

- 能力：FFmpeg 重编加了 `--enable-d3d11va` 与 `h264/hevc/vp9/av1/mpeg2/vc1/wmv3` 的 `d3d11va` 与 `d3d11va2` 两组 hwaccel（`d3d11va2` 才能接设备上下文；Makefile 只给 `d3d11va` 编 `dxva2_*.o`，所以两组必须一起开）。体积 +70KB。
- 代码：`decoder` 里进程级建一次 `AVHWDeviceType=D3D11VA` 设备，`avcodec_get_hw_config` 确认这份构建有这个 codec 的硬解、`av_hwdevice_get_hwframe_constraints` 取分辨率上限、`get_format` 回调只在 FFmpeg 给出 `AV_PIX_FMT_D3D11` 时接受，取到的帧经 `av_hwframe_transfer_data` 回读再走原来的 sws_scale。策略在 Go（`hwUse`），机械在 C。
- **实测（RTX 3060，本机）：回读比软解更贵**。同一条管线，1080p h264 软解 1.05ms/帧 → 硬解 8.6ms/帧；4K60 HEVC 4.1 → 39ms/帧。原因是渲染器只吃 CPU 像素，每帧都要 `Map` 一次 staging 纹理，强制等待 GPU 完成，且随分辨率线性上涨。并行管线（ffmpeg CLI 实测 1.87ms/帧）靠解码与回读重叠才能掩盖这段延迟，我们是同步的 `Next()`。
- 结论：**自动路径仍然软解**（`hwPreferred=false`），启动时连设备都不建（建一次约 150ms，会把首帧从 37ms 拖到 190ms）；`CUPBOX_HW=on` 可以强制走设备、`off` 强制软解，用于对比和以后的零拷贝验证。日志里 `hw:` 开头的行会写原因。
- 四层兜底（即使强制打开也不会卡死）：构建期没有该 codec 的硬解 → 不试；建不出设备 → 全程软解；每个文件检查分辨率上限与驱动是否接受（`avcodec_open2` 失败、或 `get_format` 落到软件格式）；运行期第一帧报错、或连续 3 次回读失败 → `cd_switch_cpu` 重开解码器、seek 回上一个已显示帧继续，画面不黑不断。失败结论按 codec/profile/分辨率记在进程内，下次启动重试。
- 下一步（要真有收益）：零拷贝——把设备纹理直接交给渲染器，见 §11。
- 验证：PowerShell 中执行 `$env:PATH="$PWD;"+$env:PATH; go test ./...`，确保子包测试进程也能找到根目录的 FFmpeg DLL。回归覆盖样片首帧、跳转、MP4 音频和浮层显隐、跨帧率淡入淡出。

## 1. 一句话

双击 MP4 → 无边框窗口按视频原分辨率弹出 → 立刻播放，全程只有空格、方向键、滚轮和底部一条 32px 进度条。

## 2. 分工

```
┌─────────────────────┐   Frame{T+RGBA}   ┌──────────────────────────┐
│ decoder（独立）      │ ────────────────► │ mygo（界面与渲染）        │
│ MP4 解封装 + 解码    │                   │ 无边框窗口 / ui.Image     │
│ 只管吐帧和声音 PCM   │ ──PCM───────────► │ mygo audio / 进度条 / 输入 │
└─────────────────────┘                   └──────────────────────────┘
```

- **decoder 不知道窗口、UI、mygo 的存在**，只提供 `Open / ReadVideo / ReadAudio / Seek / Close`。
- **mygo 不知道容器和编码的存在**，只消费 `image.RGBA` 和 float32 PCM。
- 音频不经过渲染路径：解码器交出 PCM，由 mygo 的 `audio.Player` 直接送系统音频输出（Windows 上是 WASAPI，纯 Go）。这正好符合你"音频不参与渲染"的要求。

## 3. 已实测的 mygo 能力（spike/probe，本机）

| 指标 | 实测 | 说明 |
| --- | --- | --- |
| 进程启动 → 首帧上屏 | **62ms** | Frameless 窗口 + 1080p 位图，已含 Go 运行时与 D3D11 初始化 |
| 1080p 帧持续更新 | **59.9 fps** | 每帧 `Bitmap.Update` + 重绘，窗口 960×540 显示 1080p |
| 每帧 CPU | **1.4ms** | 含 8MB RGBA 纹理上传；约占单核 10% |
| 二进制 | 14MB 单文件 | 无外部依赖、无 WebView、无 cgo |

结论：**渲染这层余量充足**，1080p60 之后还要花的是 YUV→RGBA 转换（我们做，多线程约 1–2ms/帧）和解码本身。

## 5. 解码器选型（唯一待定项）

| 方案 | 体积 | 硬解 | 跨平台 | 工作量 | 备注 |
| --- | --- | --- | --- | --- | --- |
| A. FFmpeg 精简构建（cgo） | 静态链入后 exe 约 25MB | 可（D3D11VA 等，后加） | 一套代码三平台 | 小 | 只开 mov demuxer + h264/aac decoder + swresample，LGPL |
| B. 系统解码器（Windows Media Foundation） | 0 额外体积 | 是（DXVA） | 每个平台一套代码 | 大 | 非开源库，需写 COM/purego，macOS 另写 VideoToolbox |
| C. 纯 Go 解码库 | 最小 | 否 | 是 | 无解 | 现存纯 Go H.264 解码器只支持 IDR 帧（如 hi264），放不了真实视频 |

推荐 **A**：一份代码跑三平台，硬解以后按平台插 `hwaccel` 即可，许可证 LGPL（不启用 GPL 组件），静态链接后是单文件 exe。本机已有 MSYS2 mingw64，cgo 链路通。

关于"硬解"要说清一件事：mygo 的 GPU 设备是它自己的，**没有暴露"把外部 D3D11 纹理当帧显示"的接口**，所以即使硬解，帧也要从 GPU 回读到内存再交给 mygo。硬解省的是 CPU 解码开销，不是内存拷贝。要做到零拷贝，得给 mygo 加一个纹理注入 API（可作后续 PR）。

## 6. 帧交接协议

```go
// decoder 包对外的全部契约
type Info struct { Width, Height int; Duration time.Duration; FPS float64 }

type Decoder interface {
    Open(path string) (Info, error)      // 只读头部，不解码
    ReadVideo() (*Frame, error)          // 阻塞到下一帧或 EOF
    ReadAudio() ([]float32, error)       // 交错 stereo float32
    Seek(t time.Duration) error
    Close() error
}

type Frame struct { PTS time.Duration; RGBA []byte; Stride int }
```

- 帧格式统一 RGBA（视频不透明，alpha 恒 255，与 mygo 的预乘格式天然兼容）。
- YUV→RGBA 在解码器侧多线程完成，UI 线程只做 `Bitmap.Update`。
- 时钟：以音频为主时钟；视频帧按 PTS 追音频；追不上则丢帧，追上则等待。音频设备冷启动（WASAPI 唤醒蓝牙耳机、音频服务刚起来）可能长时间不推进，此时画面最多等 600ms，之后改用自己的时钟先播；设备真正出声后，声音 seek 到画面当前位置再接管时钟，画面不会跳回开头，也不会长期领先声音。
- 帧队列 4–8 秒，seek 时全量 flush。

## 7. 启动时序（按实测 62ms 重排）

```
t=0     进程启动
+5ms    argv 解析
+20ms   解码器探测：仅读 MP4 头部拿宽高/时长（moov 在尾部的文件走 seek 定位，不整读）
+45ms   创建隐藏的无边框窗口（内容尺寸 = 视频尺寸）
+90ms   创建 Bitmap + 首帧解码 + RGBA 转换
+120ms  show 窗口 + 首帧上屏 + 音频开播
```

目标：**首帧 p95 < 250ms**。规则不变：首帧就绪前不 show、探测不解除码器、不起子进程、不整读文件。

## 8.0 浮层设计

- **遮罩**：底部 72px，从透明到 `rgba(0,0,0,0.55)` 的竖向渐变，随浮层一起淡入淡出；停在字幕下方，不改变“字幕无背景”的原则。
- **进度条**：命中区仍是贴底 32px（好点、好拖），信息区增加帧率、原始分辨率、平均视频码率、平均音频码率（未知显示未知，无音轨显示无音频），两行居中并随浮层显隐，窄窗口按宽度缩小字号；底部渐变与悬停区域为 112px。视觉只在离底 20px 处画 3px 细线，左右各内缩 20px，圆角 1.5；悬停 5px、拖动 6px（120ms 过渡）。轨道 `rgba(255,255,255,0.26)`，进度用品牌黄 `#FFD60A`（0.95）；悬停/拖动时播放头处出现 9px 圆点 + 14px 的 16% 光晕。
- **时钟**：居中、位于进度条上方 10px；当前时间 15px/600/白 92%，分隔符 ` / ` 13px/白 30%，总时长 13px/白 42%；全部补零等宽，秒数跳动不抖。浮层进入时整体上移 6px（`(1-alpha)*6`）。
- **音量**：右下角、与时钟同基线，内缩 20px，12px/白 45%；滚轮调整后 0.7 秒内亮到 90% 再回落。
- **拖动时间胶囊**：仅拖动时出现，在进度条上方 72px；11px 白字、`rgba(0,0,0,0.62)` 底、8px 圆角，水平跟随指针并夹在窗口内，显示目标时间。
- **空窗口**：25% 透明的 Cupbox 图标 88px，下方 `把视频拖到这里` 17px/白 62%，再下方支持格式行 12px/白 30%。
- **动效**：进入淡入 + 上移 6px，退出只淡出（约 0.3 秒走完）；条高变化 120ms；所有元素共用一个 alpha。指针停在底部 72px 的浮层区域时一直显示；在其它位置，只有**位移超过 5px** 才算一次操作（手搭在鼠标上产生的 1–2px 抖动不算），否则 0.1 秒后开始淡出；指针移出窗口立即进入 0.1 秒计时；任何按键或滚轮都让浮层重新亮起。指针是否还在窗口里，用 `GetCursorPos` + 窗口矩形实时判断，而不是相信“最后一次移动事件”——鼠标滑出窗口后不会再有事件，用旧坐标会把浮层永久卡在显示状态。暂停时不重绘，所以浮层可见期间每 150ms 唤醒一帧复查指针位置。

空状态：不带参数启动时，窗口 960×640、纯黑，中央一行半透明白字「把视频拖到这里，或双击视频文件播放」。空窗口可以拖动，按一次 Esc 直接关闭（没有内容可丢，不需要二次确认）；其它操作不响应。

拖放：把文件拖进窗口即开始播放；正在播放时拖入新文件会立刻换片、从 0 开始，窗口改成新视频的尺寸（全屏中会先退出全屏），并就地换成新视频的尺寸——不居中、不挪位，只有窗口超出显示器工作区时才轻推回来。文件拖动悬停在窗口上时**完全不取帧、不重绘**，让系统的拖动图标能立刻拿到响应；移开或放下后自动追上音频时钟。

播完：停在最后一帧 1.2 秒，然后回到 960×640 的待拖入窗口（**留在原位**、显示提示文字），保留最后一帧作为背景，等比铺满窗口并做 30/100 强度的高斯模糊（应用内 0–100 标度，30 对应结束窗口中的约 30px sigma）。不使用文字圆角底，两行提示文字使用 700 粗体、灰白色（#E4E6E9），字号在初始值基础上放大 50%（主提示 25.5px、格式行 18px），无描边，新增独立一行「按空格键重新播放」，文字和图标保持清晰。复用 imaging 组件，结束时在半分辨率上生成一次并缓存，重播或换片后释放模糊背景。解码器和音频资源释放，可以直接再拖下一个文件。结束后按空格从头重新播放刚才的视频（最后一帧停留期间也有效）。首次无参启动仍显示黑色背景，空格无操作。

多窗口：**一个文件一个进程，一个进程一个窗口**，不再有单实例锁。每次双击 mp4（或双击 exe）都开新窗口，彼此完全独立：各自的解码器、音频、时钟、字幕、进度条、全屏与退出。新窗口从当前最靠前的 Cupbox 窗口右下角偏移 30px 级联；放不下就回到居中。

窗口移动直接在鼠标按下、移动、松开事件中处理，与视频帧解码/绘制的更新节奏分离，拖动静态窗口不启动动画循环。拖动窗口有 4px 阈值：按下后指针移动不超过 4px 视为点击，不移动窗口。

时间：固定在进度条正上方 8px 处、水平居中，不随播放头移动；`rgba(255,255,255,0.75)`，13px；格式 `mm:ss / mm:ss`，超过一小时用 `h:mm:ss`。时间文本右侧 14px 处是音量百分比（`rgba(255,255,255,0.6)`，13px），随滚轮即时变化。

## 8.1 字幕

- 来源：**文件自带字幕轨**（MKV 的 ASS/SSA、MKV/MP4 里的 SRT 与 mov_text、PGS/DVD/DVB 图形字幕）和外挂 SRT（与视频同目录同名，大小写都试）。两样都有时优先外挂。
- 编码：先按 UTF-8 读；不是合法 UTF-8 时按 GB18030 解码（覆盖 GBK/GB2312），中文常见的老字幕不会乱码。
- 解析：标准 SubRip 块；`<i>`、`<b>`、`{n8}` 之类的标签剥掉，保留换行；时间戳兼容 `,` 与 `.` 毫秒分隔。
- 渲染：系统字体，**不加背景条**，只在右下各偏移 1px 叠一层 `rgba(0,0,0,0.45)` 的阴影保证白画面也能看清；每行各自在 X 方向居中，底边距窗口底 76px（32px 进度条 + 时间行 + 间距），进度条显隐都不会盖住。
- 内嵌字幕：解析 ASS 的对齐（`\an1`–`\an9`）、字号（`\fs`）、颜色（`\c&HBBGGRR&` 与样式 PrimaryColour）、换行（`\N`），字号按 `窗口高 / PlayResY` 缩放；其它特效标签（`\pos`、`\move`、旋转、卡拉 OK）先忽略。
- 图形字幕：PGS / DVD / DVB 解出的调色板位图在 C 侧转成 RGBA，按字幕流的画布尺寸（PGS 常见 1920×1080，与视频尺寸不同）缩放到画面位置；一张图持续到下一个 display set，清屏事件会结束它。
- seek：跳转前先把字幕上下文回退 15 秒、解码到目标点，因此拖到某句中间也能立刻看到这句，而不是等下一句。
- 图形字幕的细节（PGS 的淡入淡出、DVD 的强制字幕标记）暂不处理。
- 播放中每帧重绘，字幕切换误差小于一帧；暂停时静止，seek 后立即重画。

## 10.1 解码方式

当前是**软解**：libavcodec 在 CPU 上解码，开了多线程（`thread_count=0`，frame+slice 并行）。1080p 够用；4K 会明显吃 CPU，硬解（D3D11VA）留到 M3 之后，接口上只需要在 `decoder` 里加一条 hwaccel 路径，帧仍然回读成 RGBA 交给 mygo。

## 10.2 打包

- **FFmpeg 最小构建**：源码 `release/8.0`，MSYS2 + mingw64 编译，`--disable-everything` 后只开上面 D2 列出的容器/解码器/解析器，另加字幕解码器（ass/subrip/movtext/webvtt/pgssub/dvdsub/dvbsub）与 zlib（MKV 压缩字幕轨需要），LGPL v2.1，不开 x86asm（机器上没有 nasm）。DLL 合计 **10MB**（原通用构建 165MB）。
- **打开失败**：损坏或不支持的视频弹一个原生 `MessageBox`（标题 Cupbox、一行错误）；**纯音频文件（mp3/flac/wav…）直接静默退出**，不开窗、不提示——Cupbox 只播画面。拖入纯音频同样忽略，正在播的片子不受影响。
- **安装包**：NSIS，`packaging/cupbox.nsi`，**按用户安装**（`%LOCALAPPDATA%\Programs\Cupbox`，不需要管理员权限）。产物 `dist/Cupbox-Setup-0.2.0.exe` 约 **6.8MB**。安装目录除 FFmpeg 的 5 个 DLL 外，还必须带 `zlib1.dll`（avformat 解 MKV 压缩字幕轨）与 `libwinpthread-1.dll`（avutil 的线程库）——这两个在开发机上来自 MSYS2 的 PATH，新机器上没有，缺了会报“找不到 zlib1.dll”。`packaging/build.ps1` 会自动从 `.tools/ffmpeg-min/bin` 和 `C:\msys64\mingw64in` 补齐。
- **便携版**：`dist/Cupbox-0.2.0-portable.zip` 约 **9MB**，解压即用。
- **关联注册**（HKCU）：ProgID `Cupbox.Video`（含 `shell\open\command`、`DefaultIcon`），16 种扩展（mp4/m4v/mkv/webm/avi/mov/flv/ts/m2ts/mts/mpg/mpeg/vob/wmv/asf/ogv）都写进 `OpenWithProgids` 与 `Capabilities\FileAssociations`，另有 `Applications\cupbox.exe`、`RegisteredApplications`；卸载时全部清除，并顺手清掉旧版本用过的 `Cupbox.mp4`。
- **默认播放器**：Windows 10/11 禁止安装程序静默设置默认程序，只能注册“可成为默认”的资格。安装完成页提供默认勾选的按钮，直接打开 `ms-settings:defaultapps` 让用户选一次；右键“打开方式 → 始终使用”同样生效。
- 重新打包：`powershell packaging/build.ps1`。

## 11. 为什么不给 mygo 加纹理 API（v1）

可以加，而且路径清楚，但算下来 v1 不划算。

改法（如果要改）：mygo 的渲染是 `internal/gpu/{d3d11,metal,gl}` 三套后端 + `internal/render` 场景提交，D3D11 后端自己创建设备、用 `UpdateSubresource` 上传 RGBA。要支持零拷贝，得动三处：

1. `internal/gpu/d3d11`：暴露 `ID3D11Device`，新增"外部纹理"图像类型与 NV12/P010 采样路径（Metal 用 `CVMetalTextureCache`，GL 用两个平面纹理）。
2. `internal/render` + shader IR：新增一种图像种类，Video 帧走 YUV→RGB 的 shader 变体，而不是 RGBA 采样。
3. `ui`：公开一个低层构造函数（`ui.NewTextureFrame(...)`），文档与三平台测试。

粗估 400–800 行，跨三个后端。收益：省掉每帧 8MB（1080p）上传和一次 GPU→CPU 回读，约 1–2ms/帧；4K 则省 5–6ms/帧，才有明显意义。

代价不在代码量，而在两件事：mygo 开源两天、周更破坏性变更，改它就得长期 rebase；以及在没有真实播放器跑通之前，API 形状大概率是错的（该给纹理还是给帧回调？谁管生命周期？seek 时怎么作废？）。

所以顺序是：v1 走 CPU 帧（实测 1080p60 有余量），跑通后带着真实约束去提 PR；上游不收再 fork，那时的代价可控。硬件解码不受这个限制——FFmpeg/MF 硬解后回读成 RGBA 一样能走这条路，只是多一次拷贝。

**2026-10-22 补实测**：这一节当年只是“约 1–2ms/帧”的估计，实测差了一个数量级：同一管线里硬解 + 回读 1080p 要 8.6ms/帧（软解 1.05），4K60 要 39ms/帧（软解 4.1），因为同步回读每帧都要等 GPU。所以“多一次拷贝”不是小事，零拷贝不是优化项而是前提。
